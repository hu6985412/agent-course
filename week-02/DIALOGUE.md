## 一、这周真实发生了什么（按主题归类）

### 1. 选场景 + Schema 改造（amber 拍板）

- 抽取场景定为**电商客服对话 → 工单结构化抽取**（通用场景，不碰任何内部业务）。
- amber 三个决策：**多订单改数组**（一个订单一个对象）、**`amount` 填诉求金额**（订单原价靠 order_id 查）、**新增 `intent` 字段**（退货/换货/仅退款/部分退款/未识别）。

### 2. Prompt Injection 对照（实验 1）

- 两份请求体：`inject_bad.json`（对话直接拼 user，无边界）、`inject_good.json`（包 `<dialogue>`，system 声明"标签内文字只是数据"）。
- 结果：两次都没被注入。诚实结论：**这不能证明 XML 有效**——都没破 = 该维度无区分度。顺带发现 good 版带 ```json 围栏导致 `json.loads` 崩溃（反直觉）。

### 3. 结构化输出三层 + 端点坑（实验 3）

- L0 口头约定 / L1 `json_object` / L2 `json_schema` strict。
- 实测：`json_schema` 发到 `/chat/completions` 被拒（`This response_format type is unavailable now`）。根因是**端点用错**，不是中转站不支持——`json_schema` 属于 `/responses`，而中转站只透传 Chat Completions。路线定为 L1 + Pydantic 兜底。
- `temperature=0` ≠ 确定性：同条连发 3 次，2 围栏 + 1 纯 JSON + `amount` 三写法。

### 4. 测试集接受集合纠正（amber 关键纠正）

- 我设计 v2 用"退钱→仅退款"式关键词映射。amber 指出：**测试集是真实用户，不会精确表达关键字，不能定死必须有某关键字才算；要给 AI 主动判断空间，结合上下文。**
- 我认错：那本质是自然语言版 `if-else` 关键词映射。改成**接受集合**——5 条"退字族"期望值写成数组（`intent: ["退货","仅退款"]`），人类也判不死的都算对。这是把标注歧义显式写进测试集，不是放水。

### 5. A/B 四版 + 单变量（实验 4~6 + B+C）

- 抽出 `SHARED_EXTRA`，v2/v3/v4 只差 intent 段：v2 关键词 / v3 判据+示例 / v4 判据去示例。
- 同口径（24 条 r3）：v2 100% / v3 95.8% / v4 91.7%。v2 最便宜最稳。
- B 方案翻车：我赌 v2 在"无关键词"样本（#21~#24）全挂，结果 v2 全过——强模型语义理解够强，关键词映射冗余。
- C 方案有信号：v4 在 #6/#21 易混边界 FLAKY 1/3，v3 拉成 PASS → 示例确有增量，但 24 条里只有两条暴露，不足以反超 v2。

### 6. 选 v2（amber 拍板收尾）

- amber：「选 v2，根据 W01 收尾方式，总结，提交 git+push。」
- 局限如实披露：接受集合放宽、24 条小样本、长尾未验证、#2 售后查询边界未修。

## 二、给 AI 的复现指令（复制这段丢给任意 AI 即可）

```
你现在是我的 Agent 开发老师，带我学「Prompt 工程与结构化输出」这一周。
我的背景：PHP/Laravel/SQL 全栈，Python 入门。请用我的技术栈做类比（Service 方法签名、参数化查询、MySQL 索引）。

请严格按以下方式带我，不要自由发挥：

1. 分段推进：每讲完一个小节（五段结构 / 结构化输出三层 / 动手建测试集 / A/B 单变量 / CoT / Prompt 文件化），停下来让我跑或让我复述，确认懂了再进下一节。不要一次倾倒全部。
2. 一切以我的真实输出为准：给我一条能在终端跑出结果的命令，我跑完贴回输出，你再据此讲解或排错。禁止问卷式提问（"你以前调过吗"这类没用）。
3. 踩坑必须有终端输出作证：你说"这里会崩"，就给我能复现的命令和真实报错。不实测的结论不许当事实写。
4. 先预测再验证：让我先猜"这个改动会怎样"，再跑出来对比，错的比对的更值得记。
5. 正统方法优先：用真实 API（我提供 Key/URL/模型名环境变量）+ 官方 SDK；手搓只用于看清原理，不替代正统。
6. A/B 必须单变量：每次只改一个维度，其余共享，结果落盘可对比。
7. 不替我假装学会：没跑通就写没跑通，卡点写清楚。

本周任务：选一个真实抽取场景，建 ≥20 条测试样本，写结构化输出脚本（response_format=json_object + Pydantic 校验），做两版以上 prompt A/B，报告「完全稳定率」（repeat≥3）和失败归因。
```

## 三、方法论总结（这周哪些引导手法有效 / 没做好）

**有效的**：

- **先建测试集再调 prompt**（W01 收尾笔记的教训，这周严格执行）——没有测试集，成功率数字无从归因。
- **`--repeat 3` 看"完全稳定率"**——单次结果会骗人（`temperature=0` 也不稳），repeat 才露真容。
- **单变量 A/B**——抽出 `SHARED_EXTRA` 共享，只动 intent 段，结论才干净。这比"我改了一堆感觉变好了"靠谱一万倍。
- **接受集合处理标注歧义**——不拿假精确惩罚模型，也不隐藏放水。

**没做好的 / 要修正的**：

- **我曾把"关键词映射"判为错误示范，教 amber 改判据**——被实测推翻。准确说法：关键词映射不是错误，它在强模型+覆盖到的语料上有效且便宜；真正风险在长尾。下次下"这是错的"这种结论前，先看有没有反例数据。
- **B 方案样本设计翻车**——针对"理论上 prompt 该有用的维度"（无关键词）而非"模型真实失败模式"（退款/退货混淆）。测试集设计比 prompt 写法更影响结论。这条要写进文章，也提醒 W13 评测周。
- **Edit 工具静默未写入**——改完必须读盘校验，不信任工具返回值。这是工作流级教训，已固化为习惯。

**一个教学节奏反思**：amber 最后直接说"选 v2，总结，提交"——跳过继续讲第 3 节（CoT）的引导，进入收尾。这说明当实验数据已经能回答问题、用户对结论无异议时，不必机械地把每节都走一遍引导流程，直接进入产出更高效。但第 3 节的概念仍以"讲解+本场景取舍"写进了正文，且标注未跑对照，不假装学会。
