## 二、对话实录

> 以下按主题还原。为可读性做了压缩，但**所有输出、错误和判断都是原始的**。
> 我的失误也没有修饰——它们在这份文件里的价值跟正确答案一样高。

### 主题 1 · Embedding 端点选型：从"想偷懒复用中转"到"实测 503 转向百炼"

**原计划**：复用中转站 Key 调 embeddings，零成本。我给了 bash 验证命令。

**第一处曲折（对方提问）**：
> "中转站 Key 能不能做 embedding？阿里云百炼（DashScope）Key 行不行？"

我列了三方案（中转 / 百炼 / Ollama）并给验证命令。对方选择先验证中转。

**真相反转**：对方跑出来 `/embeddings` 返回 `HTTP 503` 空 body，但 `/chat/completions` 正常。
我最初注释里写"404=未转发路由"是充分条件而非唯一判据，503 不能直接定论。于是给了一版**带响应体打印 + chat 端点对照**的脚本定位根因。

**结论（对方贴回）**：`CHAT OK` + `EMB FAIL HTTP=503 body=`（空）。
**我的修正**：chat 正常 + emb 503 空 body = **中转只代理了 chat，没接 embeddings 后端**，与账号无关。路径①排除。

**第二处曲折（对方提问）**：
> "模型使用 qwen3.7-text-embedding-flash 是否可以？"

我联网核实 2026 现状：该模型**可用且优于**原本定的 `text-embedding-v3`——1024 维、20 条/批、单行 128000 token、¥0.125/百万、201 语种、带 sparse。对方验证 `OK 维度 = 1024`。**endpoint 敲定百炼 flash。**

**教训**：端点选型不能凭记忆或想当然，**先实测再下结论**；503 不等于"不支持"，要看 chat 对照 + 响应体。

### 主题 2 · 四节概念引导（对方每节都抓到了核心）

- **第1节 Embedding**：对方一句话概括"mysql 全文检索必须包含退款二字，向量检索算向量远近"——抓到了"字面包含 vs 语义距离"的本质。我补了"全文检索仍有用，W06 混合检索融合"的伏笔。
- **第2节 余弦**：对方复述"Embedding 关心语义方向是否相近，余弦只比方向忽略长度，刚好合适"，并正确判断 SQL 里 `ORDER BY embedding <=> :query_vec` 是升序、LIMIT 拿最像的。两个 check-in 全对。
- **第3节 切分**：对方答"切太大混多话题平均不准、切太小丢上下文易被挤出 top_k"，并选 structure（规范 Markdown 按结构切）。我补了"recursive 是默认首选（结构优先、缺失兜底）"。
- **第4节 向量库**：讲了 pgvector 核心优势（向量即列、能 JOIN/WHERE）+ HNSW vs IVFFlat。

### 主题 3 · 切分实验 A/B：亲手实证"召回质量头号开关"

对方本机跑完实验 A（400/80，4 chunks：show-all / top_k=3 / 阈值 0.3）和实验 B（120/0，18 chunks）。

**我给的关键结论（nuanced，不是简单说"切太小不好"）**：
1. 实验 B 最佳块从 0.6482 跳到 0.7310——**"切太大→平均后不准"被实证**（默认块混了账户登录尾巴稀释退款语义）。
2. 但 120/0 不是好配置：零 overlap 有劈句风险（03 已证）、18 块存储翻 4.5 倍、长文档相关块易被挤出 top_k。
3. **没有一刀切的 chunk size**，适中 + 合理 overlap 是稳健默认，但应按文档和查询类型调。

### 主题 4 · 03 脚本结论 bug：演示代码也要验证

第一版 `03_bad_case.py` 写"『银行卡退款需3至7个工作日』被劈成两半"，但**实际跑出来这句完整**，被劈的是前一句"退款申请…完成审核"。我凭记忆写死了结论文字，没对照运行输出——这是假演示。修正为 fixed 硬切让句子真被劈，结论据实改，重跑验证通过。

**教训**：演示代码也必须跑一遍，**现象和结论要对得上**，否则就是编的。

## 四、方法论总结（这一周沉淀下来的）

1. **端点选型先实测，别猜**：中转站 503 差点误判成账号问题。判定"某端点是否支持 embeddings"的正确姿势是 chat 端点对照 + 打印响应体，而不是看状态码下结论。
2. **演示代码也要验证现象和结论对得上**：03 第一版结论是我凭记忆写死的，和实际运行不符。任何"演示某个 bug"的脚本，必须真跑一遍确认它演示的就是它声称的现象。
3. **chunk size 没有一刀切**：实验 B 证明聚焦短答案小切分更准，但零 overlap 有劈句风险。最佳实践 = 适中切分 + 合理 overlap，按文档和查询类型调。
4. **PowerShell 5.1 的坑要提前规避**：`curl` 是 `Invoke-WebRequest` 别名、GBK 乱码。验证类任务用 `Invoke-RestMethod` 或 `curl.exe`，正式调 API 用 Python（`requests` 默认 UTF-8）。
5. **诚实披露胜过漂亮数字**：BM25 混合检索留 W06、03 结论 bug 已修正、实验 B 改完没重跑库——这些都如实写进正文，不假装一次写对。
